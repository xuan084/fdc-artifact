## 0. Disclosures (deviations)

1. **The contribution is computational.** FDC-DP's certificate is FDC-BF's (Theorem DP-1 in `plan/fdc_dp_theory.md`; external reviewer r1: valid). What is new is exact certification over implicit policy classes (up to about 10¹⁹ policies at S = 64) by exact union counting, a multiple-choice knapsack form of the certificate and an exact branch-and-bound that abstains at a node cap.
2. **ε was chosen on dev by the pre-stated rival-success rule.** The rule (`plan/v10_plan.md`, written before the ε ≥ 0.03 dev runs) picks the smallest ε on the declared grid at which the dev-best of the two named rectangles has strict N80_pen < τ on ≥ 40/50 dev streams. It never looks at FDC-DP. It is implemented in `run_fdc_dp_dev.select_eps` and was applied mechanically to the v2 dev results (after the external reviewer fixes). The cells it selected are the confirmatory cells; X5 S = 64 had no qualifying ε and is descriptive.
3. **Table reuse.**
   - The **X5 eval half** is used for the 3rd time: v8 A (seeds 35000–35199), v9 B (37200–37399).
   - The **Lenta LR9 eval half** was used by v6 B (32000–32199) and v7 B (34000–34199), both descriptive, and the table is **outcome-exposed**: r4 computed full-table LR8 cell means that include these rows (v6 exposure statement). v10 B is its first confirmatory use and its 3rd fresh-stream use. (The design note called this the 2nd use; the v6 B use is added here.)
   - Only the seeds and the segmentations are new. Fresh seeds give inference over new replay randomness **conditional on these reused finite tables**; they are not a fresh holdout and not an independent-table replication.
4. **HC-WoR-DP is an untuned transfer.** Its configuration is the frozen v8 S = 9 setting (X5 ← X9 config, Lenta ← CR config) at the 50/50 plan; target cell sizes are recomputed from the new weights. It is descriptive only, and no claim of superiority to a well-tuned HC implementation is made.
5. **Claims are restricted to the named rectangle implementations** (RECT-BF-DP-TU as the matched rival; HC-WoR-DP as an untuned transfer), never "the best valid rectangle" (external reviewer r1 §4).
6. **Lenta control-pool exhaustion.** Lenta is about 25 % control, so the 50/50 design exhausts control pools. On dev, RECT-BF-DP certifies only after every control pool is exhausted (0.816 τ on every stream), and at S = 16 FDC-DP(b) also needs every control pool. The Lenta comparisons are therefore exhaustion- and checkpoint-sensitive finite-table comparisons. Every cell reports the mean fraction of exhausted cells (all / control / treatment) at each method's N80 checkpoint, and a mechanism claim about pre-exhaustion widths is made only where both methods have fraction 0.
7. **Stopping horizon (dev deviation).** The v1 dev runs stopped streams at 12/15 although the theory note prespecified stop_k = 15. v2 dev and v10 run to 15/15 (or τ); N80 is recorded at 12/15 from the same trajectory, and a false stream is any false certificate over the whole run.
8. **v1 dev numbers are superseded** by v2 (weighted-centre fix B1). On these near-equal-size segmentations all 4,800 common-stream N80_pen endpoints reproduce, and hence so do the reported ratios, bootstrap bounds and ε selections. The stopping horizon (now 15/15), runtimes, recorded certificates and the branch-only count (25 vs 27) differ (`plan/fdc_dp_dev_report.md`, v2 section; external reviewer v10 lock r1 F4).
9. **ε varies with S**, so the selected-ε ratios are not a controlled scaling experiment.
10. **Frozen segmentation differs slightly from the v1/v2 dev segmentation.** Eval needs fixed cut points, so v10 uses the dev cut points with "ties at a cut go up". On the dev replay pools this reassigns 4 / 12 / 22 rows (X5, S = 16 / 32 / 64) and 231 / 628 / 2,166 rows (Lenta) relative to seg_v10's seeded tie-break. The v10 dev runner check (§6) uses the frozen segmentation.

## 1. Methods

All methods use the frozen 50/50 design (`balanced_alloc(S, A, 0.5)`), the same arrivals and pool orders, the K = 20 checkpoint grid as both block grid and monitoring grid, δ = 0.05, and the frozen problems.

| Role | Method | Definition | Guarantee |
|---|---|---|---|
| **Primary** | **TU-FDC-DP(b)** | `fdc_dp.FDCDPTimeUniform(ck, scheme='b')`: FDC-BF cells (Bennett-FPC, exact-HG variance box at δ_var/(2SAK)), δ split (0.045, 0.005), ledger β = ln(Σ_q \|Π_q\| · K / 0.045) by exact counting DP, one λ grid per checkpoint (ratio 2000^(1/160)), scheme (a) then exact B&B, node cap 2·10⁵ (abstain), weighted centre | FWER ≤ 0.05 for all t ≥ t₁ under the frozen outcome-free schedule (DP-1 + Lemma TU); per stream and problem family |
| **Primary rival** | **RECT-BF-DP-TU** | `rect_dp.RectBFDPTU(ck, box=True)`: matched Bennett-FPC rectangle (same cell inequality, box and split, 2SAK events), radii frozen at block points, exact DP over the policy class; parameter-free | FWER ≤ 0.05 for all t ≥ t₁ under the frozen schedule (Lemma TU) |
| Descriptive | HC-WoR-DP | hedged-capital WoR CS rectangle with the DP certificate; untuned v8 transfer | time-uniform under any predictable sampling |
| Descriptive | FDC-DP(a) | single-column scheme (a), K-checkpoint guarantee | FWER ≤ 0.05 at the K checkpoints |

Because monitoring happens only at the block grid, TU-FDC-DP(b) is numerically identical to FDC-DP(b), and RECT-BF-DP-TU to RECT-BF-DP (unit tests). No dense monitoring is registered, so no off-block claim is made (external reviewer r1 B4/§5). Fresh-width FDC-DP and RECT-BF-DP calls off the predeclared grid raise.

**Frozen segmentation and problems** (`seg_v10_eval`, hashed in `frozen_segmentation`):
- **Score model.** The seg_v10 T-learner: two HistGradientBoostingClassifier models, fixed hyper-parameters, random_state 0. They are fit on the 30 % model split of each dev half (seed 10010) and pickled. Eval scoring loads the pickles; there is no refit. A load-time check confirms that the pickles reproduce the hashed dev replay-pool scores.
- **Segments.** S − 1 cut points, which are the minimum dev replay-pool score of seg_v10's equal-size quantile segments 1..S−1. A row's segment is #{j : cut_j ≤ score}.
- **Problems.** Frozen from dev: κ[s, 1] = 8 for every segment and budgets ⌊b_q · 8S⌋ for b_q = 0.10, 0.15, …, 0.80 (15 problems; "treat at most ⌊b_q S⌋ segments"). They are not recomputed from eval weights. Policy values use the eval segment weights.
- **Rows.**
  - X5: every row of `eval_labels.pkl` in file order, with outcome from `eval_outcome.npy`; files checked against PROVENANCE.json.
  - Lenta: the LR9 eval half (complement of the split-seed-6006 dev half) of the sha-pinned `tidy.pkl`, with outcome `response_att`.
  - In both tables the whole eval half is the replay population; τ_R = N.
- **Checkpoints.** `fr.checkpoints(n_min, τ_R, 20)` with n_min 2,000 (X5) or 5,000 (Lenta).

**Endpoint.** N80_pen is the checkpoint at which 12/15 problems are first certified, if no false certificate exists by then; otherwise it is τ_R. The stream continues to 15/15 or τ_R.

**Statistic.** The paired geometric-mean ratio of N80_pen, TU-FDC-DP(b) / RECT-BF-DP-TU. It uses a paired percentile bootstrap over the 200 streams (B = 10⁴, seed 42), with one resample matrix shared by every cell and comparator, and a one-sided UB95.

## 5. Replica and integrity

- **R1.** An independent process re-runs the first 10 seeds of each eval task. Canonical rows (all fields except timing: `sec`, `rs_sec_*`) must be identical.
- **R2.** `schedule_digest` must be identical across all four methods per seed. All four use the frozen 50/50 design.
- **R2b.** `arrival_digest` (the schedule the engine actually consumed) must be identical across all methods per seed.
- **Seals and gate.** Seals as in v8/v9 (`v10_seal`: seal and sidecar ref committed alone, single-commit history anchor). The lock file is anchored by a single commit, and the gate cascades through v9 → v5. Eval outcomes cannot be obtained through any v10 reader, including the exported `read_eval_rows`, without a locked v10 addendum that lists the task for exactly that layer (tests: `test_eval_refused_without_lock`, `test_gate_runs_before_any_eval_read`, `test_eval_gate_checks_registered_layer`, `test_eval_path_on_synthetic_rows`, `test_public_read_eval_rows_is_gated`). **Scope of the integrity claim (external reviewer r1 F3):** no eval outcome has been *used* by any v10 computation before the lock. It is not literally true that no eval byte was read. `_lenta_dev` deserialises the whole Lenta pickle (eval outcomes included) and then keeps only dev outcomes. The LR9 split uses full-table covariates. Manifest hashing reads file bytes. The eval halves were also read by earlier rounds (table reuse, §0).
- **Missing runs and failures.** A failed job aborts the task (`errors.log`, no seal). Eval tasks are sealed only on a complete matrix and are never re-run once sealed.
