**Remaining blocker R2-1 (P1, residual F1): bind the requested table to the authorized task.** At `exp/code/dsswm/envs/seg_v10_eval.py:193`, authorization checks only `eval_task_id` and the independently supplied `layer`; at `:194`, the independently supplied `data` selects the actual read. `eval_gate` compares the registered layer to the caller's layer string (`:230`), but never sees `data`. The registration already includes the authoritative table and S (`plan/prereg_lock_v10_addendum_DRAFT.json:329`).

I reproduced the defect with the real `eval_gate`, mocking only `prereg_v10.addendum_gate` to represent successful lock validation and replacing `_read_eval_rows_raw` with a synthetic sentinel:

| `read_eval_rows('x5', 'v10b_full_s16', 'LENTA-SR16')` | `'x5'`, accepted under Lenta authorization |

This does not bypass the missing-lock check, and the registered constructor derives its layer from its validated table (`seg_v10_eval.py:281`), so it is not evidence of a pre-lock outcome read or a defect in the registered runner's table selection. It is a public API authorization gap: an accidental table/layer mismatch can read a different outcome table from the one authorized for that task. The new test patches `eval_gate` to always deny (`test_v10_addendum.py:298`), so it cannot detect this case.

**Blocking fix only:** validate `data` against the supported tables and the authorized task's registered `data`, and validate layer consistency with that registration's `data`/`S`, before entering the raw reader. Keep this enforcement in the shared helper used by both entry points. Add sentinel-based regression coverage for both cross-table mismatches and unknown table names, plus correctly matched success cases and missing/draft/wrong-layer refusals.
