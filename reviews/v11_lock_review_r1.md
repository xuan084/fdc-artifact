Verdict: fix-then-lock

Independent lock-v11 review, round 1, 2026-10-05. The numerical design and dev selection reproduce, but the eval gate violates the required authorization/logging order. Do not lock this implementation yet.

**F1 — P0 (blocks lock): the gate reads eval bytes before authorization is complete and before logging.** `exp/code/dsswm/stats/prereg_v11.py:117` calls `data_drift_v11` with its default `read_eval_outcome=True` (`exp/code/dsswm/envs/obd_v11_eval.py:90`). This hashes both eval files. Task membership is checked only afterward (`prereg_v11.py:122`), and the single-commit lock anchor is checked afterward still (`:151`). The reader's layer check, caller-SHA check and access log occur after that gate (`obd_v11_eval.py:248`, `:251`, `:257`). Consequently, wrong-layer/wrong-SHA calls read bytes before refusal; an unknown task or an uncommitted, otherwise valid locked JSON also reaches hashing. The runner additionally hashes outside the logged reader through `run_v11.py:337`, used by main, replica and analysis. A failed gate can therefore write `eval_touched: false` at `run_v11.py:350` despite having read eval bytes.

I exercised the real v11 control flow with an in-memory lock and a sentinel replacing eval hashing: wrong SHA and wrong layer produced `HASH -> history check -> refusal`; unknown task produced `HASH -> refusal`; uncommitted lock produced `HASH -> history failure`. No actual eval file was opened. Missing/draft locks do refuse earlier; this is not evidence that outcomes have already been inspected.

**Fix:** separate metadata authorization from eval-file verification. Validate the canonical lock, history, inherited chain, code/inputs, task, layer and caller SHA without opening either OBD eval file; append and durably flush the access record; only then hash and deserialize them. Route runner/replica/analysis data verification through that same authorized, logged operation, or use the locked data-hash mapping for row binding until the reader verifies actual bytes. Add integration tests that retain the real v11 gate and replace only filesystem hashing/raw reads with sentinels; cover uncommitted locks, unknown tasks, wrong layers, missing/wrong SHA, logging failure and successful ordering.

**F2 — P1 (must fix before lock): advertised fake-only tests touch the real sealed labels and conceal F1.** `exp/code/dsswm/tests/test_v11_addendum.py:59` builds `_fake_lock` using real `current_data_hashes(False)`, which hashes `eval_labels.pkl`. Both tests at `:64` and `:77` invoke it. The test at `:161` also invokes the real hasher for labels. Moreover, the ordering test replaces the entire addendum gate with unconditional success (`:79`), so it cannot detect the premature gate hash. The supplied full-suite command is therefore incompatible with this review's hard prohibition.

**Fix:** construct fake hashes entirely in memory and replace all data paths/hashers with synthetic fixtures in binding tests. Add a suite-wide guard that rejects opening either real eval path. Retain the real authorization control flow for F1's tests. Verify the complete suite under that guard before rebuilding the draft.

The builder's claim at `build_v11_addendum_draft.py:6` is similarly too broad. The provenance JSON also records eval-label-only statistics from split preparation.

**Fix:** consistently distinguish split preparation, label-byte hashing, label deserialization and outcome access. State that pre-lock v11 binding hashed labels without deserializing them and sourced the outcome hash from PROVENANCE; acknowledge split-time label statistics. Remove “no eval-half byte”/“no eval file opened” claims. This is a disclosure correction, not evidence of outcome leakage. If literal zero pre-lock eval-byte access is intended prospectively, source both eval hashes from the bound provenance and disclose the earlier label hashing.
